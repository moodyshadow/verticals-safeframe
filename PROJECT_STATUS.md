## Standing pipeline rules (fixed 2026-09-01/02, apply to every future video)

- **Stock media matching**: dual-provider search (Pexels + Pixabay), scored and ranked rather than accepting the first passable hit. Fixed: headline-tuned keyword extraction that dropped subject nouns, broadened-search validating against the full keyword list (not a shrunk one), a scaling relevance threshold, an "anchor word" requirement (a genuine proper-noun/brand term must appear in the match, not just generic word overlap), and **duplicate-avoidance across one video** — an asset already used in a job can't be reused for a different frame in the same job.
- **AnimateDiff/AI generation**: was silently defaulting to `enable: True` regardless of the webui's saved UI state — now explicitly disabled unless the pipeline specifically wants a motion clip. Vision QA gate uses `llava:7b` (the previously-configured `llama3.2-vision` was completely broken — wrong model architecture — and always failed).
- **Script generation (`draft.py`)**: no legible/specific text on signs/screens, no depictions of real named individuals, no fabricated facts (independent grounding check against research), no over-committing CTAs ("Part 2 tomorrow" — the option was removed from `niches/gaming.yaml` entirely), broll_prompts must be simple/single-subject (not compound scenes) and must never describe emotions/facial expressions (now an automated check with retry, not just a prompt instruction).
- **Captions**: smaller (68pt gaming / 64pt tech, was 76/72), genuinely bold font (`Arial Black`, not just the ASS bold flag), all-caps, and the highlighted active-word size now scales with the configured size instead of a hardcoded value.
- **Multi-image b-roll slots**: a single frame can now show a crossfading sequence across several real images/clips instead of just one (`animate_multi_image_frame` in `broll.py`), and real video clips can get a slow punch-in zoom (`prepare_video_clip(..., punch_in=True)`) instead of holding one static framing.
- **Published-video lock**: a video is only "final" once actually live on YouTube (`youtube_url_en` recorded on its draft) — checked automatically, not something you need to tell me. Working files (logs, superseded drafts, source images) only get cleaned up after that point.
- **Scheduled publish times** (added 2026-09-02): every upload now auto-schedules to go public at a niche-specific time instead of staying private indefinitely — gaming at 02:00 Romania time (targets US evening Shorts peak, ~7pm ET), tech at 19:00 Romania time (targets US late-morning/lunch peak). Computed fresh per upload (`upload.py`'s `_next_occurrence`) using real timezone rules (`Europe/Bucharest` via `zoneinfo`+`tzdata`), so it stays correct across DST — no fixed UTC offset to go stale in winter. CTA policy: the channel's signature closer is "Subscribe to stay overclocked on the latest {beat}" — no "like and subscribe" (a deliberately-avoided generic CTA), enforced by an automated `_check_cta()` check in `draft.py` with regenerate-on-failure, same pattern as the grounding/emotion checks.
- **Claude review gate before upload** (added 2026-09-02): `upload` now hard-blocks (`sys.exit(1)`) unless the draft has `reviewed_by_claude: true` set, which only happens via `python -m verticals review --draft <path>`. This exists because the automated llava vision-QA score has repeatedly missed real defects (a compositing halo, a reused/duplicate b-roll frame, a garbled caption word) that only surfaced once a person actually looked at the frames — the automated score is a signal, not a substitute for someone actually looking. Standing rule: **before running/approving any upload, actually look at the finished video's key frames yourself** (pull frames or a contact sheet), don't just trust the vision-QA pass/fail, then run `verticals review` to clear the gate. `--skip-review` exists only for a deliberate bypass (e.g. re-upload of something already reviewed).
- **7-day cross-video reuse cooldown** (added 2026-09-03): found by inspection that 6 of 8 b-roll frames in a freshly-produced video were pulled straight from the shared asset cache, first used just 1-2 days earlier — the old duplicate-avoidance only ever prevented reuse *within* one video, never across different videos over time. `media_library.find_in_library()` now hard-excludes any asset used in the last 7 days (`REUSE_COOLDOWN_SECONDS`) via a new `allow_cooldown_fallback` flag. Every stock-fetch function in `stock_media.py` (Pexels/Pixabay, photo/video, both the direct search functions and the `exclude_paths`-aware `fetch_topical_broll*` used by the real pipeline) now checks the library **twice**: once strictly (cooldown-fresh only) before trying a live API search, and only after a live search *also* comes up empty does it fall back to the single least-recently-used cached asset — with a horizontal mirror flip (`_mirror_asset`) applied so that last-resort case never looks pixel-identical to its earlier appearance. Getting this ordering right mattered: the first version checked the stale-cache fallback *before* ever trying live search, which meant a live search that could have found genuinely fresh footage never even ran.
- **Cooldown gap on live search results** (found and fixed 2026-09-03, same day): even with the ordering fix above, a *live* API hit was still always treated as "fresh" just because the search call itself was new — never checked against the cooldown table. Caught because Pexels/Pixabay return the same stable top result for a generic query ("circuit board macro"), so a live search kept re-serving a clip used only 7 hours earlier (`times_used: 7`) while logging it as a fresh find. Fixed with `media_library.is_on_cooldown(data, media_type)` (hashes the downloaded bytes and checks the library's `last_used_at`), wired into all 6 live-fetch acceptance points in `stock_media.py` (the shared `_download_and_cache` used by `fetch_topical_broll`/`fetch_topical_broll_video`, plus the 4 standalone `search_*` functions) — a cooldown-blocked live hit is now treated as a miss and the caller moves to the next candidate, cascading to the same mirror-flipped last-resort path a cache-only miss uses.
- **Cooldown only counts content that actually aired** (added 2026-09-03, same day, per explicit rule from the user): `times_used`/`last_used_at` used to get stamped the moment an asset was picked during generation — which meant a video that got discarded, redone, or never made it past review/upload still permanently burned its content's 7-day cooldown for nothing. Moved all stamping into a new `media_library.mark_used(local_path)`, called only from `cleanup_published.py` once a job's real YouTube privacy status is confirmed `public` (the same check the published-video-lock rule already relies on) — never at generation time. `generate_broll()` now returns a 3rd value, `used_asset_paths` (the exact library paths it drew on for that job), which the pipeline persists on the draft (`broll.artifacts.used_asset_paths`) so cleanup can mark them later; `find_in_library()` no longer stamps usage on a cache hit either. Net effect: a video's b-roll content is free to be picked again immediately if that video never actually goes live.

## Fixed 2026-09-03 (evening): stray SD_WEBUI_URL override
A persistent Windows **User-level environment variable** `SD_WEBUI_URL=http://127.0.0.1:7861` (Forge) had been silently overriding `broll.py`'s own default (`http://127.0.0.1:7860`, the main A1111 webui) for every process on this machine, set via `setx` at some earlier point in this project's history and never cleaned up. This meant **every automated gaming-niche production run** (which needs the main webui specifically for AnimateDiff — Forge doesn't support it, a known incompatibility — and for img2img reference-photo generation) was silently being routed to Forge instead, causing AnimateDiff to report "not available" and falling back to plain stills, and img2img calls to fail outright with connection errors once Forge wasn't running. This was discovered while manually re-running production and is a plausible root cause for some of the degraded/generic gaming b-roll seen earlier this session, independent of the anchor-keyword and cooldown bugs already fixed. Removed via `[System.Environment]::SetEnvironmentVariable("SD_WEBUI_URL", $null, "User"/"Machine")` — the registry-level fix is real but only takes effect for *new* shell sessions (a running shell keeps its already-loaded environment block), so any Claude session or script running before the next reboot/relogin should explicitly pass `SD_WEBUI_URL=http://127.0.0.1:7860` for gaming-niche commands as a safety net until then.

## Fixed 2026-09-03 (evening): main webui pathologically slow without --medvram
Once the SD_WEBUI_URL routing above was fixed, real generation on the main webui (`C:\Users\szabo\stable-diffusion-webui`, no xformers installed) turned out to be genuinely broken under sustained use: VRAM usage sat at 7.2/8GB (an 8GB card) and generation speed degraded to ~6-16% progress with 30+ minute ETAs — a classic VRAM-pressure/paging symptom, not a hang. A quick restart temporarily "fixed" it (fast again right after restart) but it degraded again within 1-2 frames, confirming it's a resource-pressure problem, not one-off bad luck. Fixed by adding `--medvram` to `COMMANDLINE_ARGS` in `webui-user.bat` — confirmed via a timed test request: 12.4s for a full generation immediately after the medvram restart, versus 30+ minutes before. If this recurs even with `--medvram`, the next step would be `--lowvram` or actually installing xformers (currently absent — "no module xformers" appears in every startup log).
